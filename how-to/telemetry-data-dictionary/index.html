Understanding Game Data

Downloaded game records can help you examine recorded responses, performance, and patterns worth discussing in class. Available data and field structure depend on the activity and export version.

  • Use Class Answer Analysis for supported question-response CSVs. Available wording and answer distributions depend on saved question details; files stay in your browser.
  • Check the export-format comparison before interpreting fields.
  • Read Responsible Telemetry Use for interpretation limits and handling student-submitted records.

The detailed field dictionary covers all 137 fields in the shared RPG CSV (mq-rpg-csv/1): Faculty Composer / Arcane Archive, Economic Realm, Managerial Intelligence Directorate, Micro Domains and Macro Command System.

Shared RPG — Detailed Field Dictionary

The definitions below cover every column in the unified RPG report. A field is populated only when the game records an applicable observation. A mode absent from a game remains unavailable. Historical defaults described in individual notes apply to older exports only; current missing numeric values are blank.

A shared layout makes it easier to combine files and compare the same measurements. It does not make different games’ scores, question difficulty or completion requirements equivalent. Response times, focus changes and copy events require context; they do not establish learning, motivation, engagement or misconduct. Labyrinth does not measure visibility, focus or copy behavior, so those cells remain blank.

Blank is not zero

Blank / null: not collected, not applicable, an older version, or a conditional measurement that has not occurred.

Measured behavioral zero: the measured duration/count was zero or the indicator was false. tabSwitchCount = 0 means no measured visible-to-hidden transitions. A blank does not.

Older columns need extra care: correctness, scores and mode-specific numbers often default to 0 on unrelated rows. Those zeros do not establish incorrect answers or measured behavior. Filter by event and mode before interpreting them.

Timing: elapsed, visible, hidden

For newly measured response rows, responseTimeMs ≈ activeResponseTimeMs + hiddenTimeMs. “Active” means the document was visible, not that the student was attentive. Visible graph or modal time remains included.

Illustrative example: a 12-second response

Assume one visible → hidden → visible trip. The final return-to-answer duration is timeAfterReturnMs; it is blank if no return occurred or the page is still hidden.

Do not add hiddenTimeMs and unfocusedTimeMs. Visibility and window focus are independent and can overlap. A window can lose focus while the page stays visible. Focus fields measure blur, time unfocused, and time since final refocus.

Version boundary: a populated activeResponseTimeMs identifies the new measurement. Older rows retain their original gameplay responseTimeMs. On new rows, gameplayResponseTimeMs preserves that original engine value. Menu/Continue starts a fresh view interval; response timing is not an uninterrupted lifetime clock.

Exam review: committed question rows aggregate recorded views of that question/room. Durations and counts accumulate; selection maxima use the maximum and region flags use “any.” Return/refocus durations come from the last recorded view, and are blank if that view had no qualifying return. Copy timing retains the latest copied view's offsets.

Choose the right event rows

Local Download Game Data: use event = question for accepted response analysis. A repeated question can represent another attempt, so do not deduplicate by questionID alone. rapid_guessing records rejected rapid attempts; examine these separately.

Exam exam_answer_initial and exam_answer_revision rows describe drafts. Committed answers appear as question with adaptiveMode = exam-commit. Do not combine draft rows with committed answers or use draft correct = 0 as incorrect performance. Completion and early-ending rows describe runs, not individual answers.

Separate path: anonymous aggregate collection

Explicitly enabled anonymous collection uses a different envelope and field names. It can repeat a response snapshot across answer_submitted, answer_evaluated, and feedback_shown. For that export, normally use answer_evaluated and restrict to accepted attempts when analyzing accepted responses. Counting all three triples the same response. That recommendation does not change the local CSV's question filter.

Aggregate build/schema IDs, sequence numbers and graph indicators are not additional columns in this local 88-field dictionary. Ordinary faculty downloads need no server tools or administrative credentials.

Behavior is interaction evidence, not proof of intent

A tab switch, long hidden interval, rapid response, selection, or copy action is not proof of cheating. Use patterns to understand engagement, compare visible and elapsed work time, investigate unusual attempts in context, improve assessment design, or support appropriate research. There is no automatic misconduct score.

The selection/copy tracker records settled selection counts, the largest selected character count, question/answer region flags, relevant copy counts, and timing to subsequent hide or blur. It inspects relevant DOM selection transiently to calculate these measurements.

This tracker does not store selected or copied text, read clipboard contents, or collect keystrokes, screen contents, unrelated-tab URLs, or browser history. This describes the behavioral tracker, not all data on the website. The CSV also contains question metadata and run identifiers; the separate anonymous collection uses random persistent client/run identifiers. See the privacy information for broader context.

Build authorization is separate from measurement

Public polished games, including Managerial Intelligence Directorate, Economic Realm, Macro Command System, and Micro Domains, remain local-only for telemetry for now. Supported gameplay records stay on the device unless deliberately downloaded and submitted; downloading a CSV does not transmit or submit it. Private or class-specific builds, including Composer-generated games, can transmit anonymous gameplay and interaction data only when the instructor/deployer explicitly enables collection. Collection is OFF by default. Ordinary collection is operational/instructional/product analytics, not research by default. Separately designated research requires its own institutional decisions and dataset handling.

You can choose to collect anonymous gameplay data when you create a game with the official Mastery Quests Composer. Collection is OFF by default. To send data, the game must be published on a supported HTTPS website. Permission to send data lasts 365 days for each generated game. Collection stops if that permission expires or is withdrawn, or if a player turns it off in their browser. Players can still play and download their game data. Data already received stays subject to the separate 730-day retention policy.

A game opened directly from a file on your computer can be played and can save a CSV, but it cannot send gameplay data to Mastery Quests. Publish the same file on a supported HTTPS website to enable collection while its permission is valid. Your LMS or network may still block data collection, so test the game the way students will open it. Anonymous records cannot confirm who played or reliably link the same player across different websites.

The National Engine uses an older data-collection setup. Check its own notice for details.

Capability digests, build scope, issuance, expiry and revocation metadata are server authorization controls, not new learner measurement fields. Raw capabilities are not analytical fields or CSV columns. HTTPS transport permission alone does not authorize collection. The measurement, governance and disclosure contract versions remain unchanged.
