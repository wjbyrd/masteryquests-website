# Feedback Lifecycle and Accessibility UI Audit

Date: 22 October 2026. Repository: `wjbyrd/masteryquests-website`. Branch: `accessibility-preview`. Audited commit: `aa74a1e2`.

This is a diagnostic report. No application source, question banks, generated games, gameplay rules, telemetry, or deployment configuration were changed. Nothing was committed, pushed, merged, or deployed.

## A. Executive findings

**Review Explanations solves a real access problem, but its current implementation is an incomplete fallback, not a complete feedback system. A permanent history is not inherently required by WCAG.** The original instructional feedback can be made accessible where it appears. Whether that should replace history depends on the mode and on an explicit decision about progression and timing.

The central problem is asymmetric delivery: ordinary correct answers usually display the question's explanation briefly and advance automatically; many incorrect answers display a setback or remediation message without that explanation. Adding a history does not repair an explanation that was never released.

| Finding | Evidence and classification |
|---|---|
| Correct explanations disappear automatically | Confirmed: canonical-derived games use 2,800 ms, Cost Directive uses 1,800 ms, and Labyrinth of Choice uses 3,200 ms. Decorative-motion pause does not stop these JavaScript transitions. The live-region text is subsequently replaced. This remains an accessibility concern. |
| Review can capture incorrect explanations | Confirmed in fresh Quiz, Trial by Graph where supported, Fading Fortune, and non-bust Risk & Reward cases. It is not restricted to correct answers. Standard Campaign's ordinary Wrong Turn supplies no question explanation, so no entry is expected there. The observed correct-only list is explainable by the release paths, not proof of a broken wrong-answer collector. |
| Review disappears at completion | Confirmed lifecycle defect in its role as an access fallback. A ten-question Market Gate quiz had eight entries after question eight and zero after completion. Timed Trial also went from one entry to zero at expiry while its menu remained open. The final correct explanation receives only its short transition window. |
| Coverage is not “all questions from this run” | Confirmed. Recovery stages, boss responses, generic setbacks, and canonical pre-boss transitions do not release the question's explanation. The collector intentionally excludes them. Replay entries are deduplicated, held only in memory, and do not survive reload/resume. |
| Exam restrictions vary materially by engine | Confirmed. Canonical-derived games withhold immediate item feedback; Managerial parity also does so. Labyrinth's Exam Drill immediately displays correct explanations and incorrect setbacks. Review itself stays unavailable there. This behavior existed before the accessibility cleanup; changing it is an assessment-design decision, not a cosmetic fix. |
| Labyrinth loses question semantics/focus after starting | Confirmed. Before start, `#question` has heading semantics and `tabindex=-1`; after the game surface is restored, both are absent. A keyboard answer then leaves focus on `BODY`. This is a separate accessibility implementation defect. |
| The long menu is real; its appearance is a design issue | Eight genuine quiz entries expanded the menu card to 2,477 px of content within an 858 px viewport at 1280×900. This is burdensome scrolling, but vertical scrolling alone is not a WCAG failure. |
| Motion selector and graph disclosure look inconsistent | Visual-design concerns, not established failures of their native controls. Shared motion behavior worked in scoped testing. Graph keyboard operation, expansion, and return focus worked at desktop and mobile sizes. Preserve the descriptions. |

**Recommendation:** improve delivery first, with owner-approved student-controlled continuation in suitable untimed instructional modes. Retain only a compact, optional route to already-released explanations where automatic progression still makes that necessary. Do not remove today's fallback until its replacement is available and tested. Do not expand it into an answer archive.

### Recovery, boss, and engine exceptions

**Repair → bridge → retest:** a natural Market Gate run entered repair after seven misses. Correct repair replaced the question with bridge immediately; correct bridge replaced it with retest immediately. Both displayed stage dialogue rather than the answered question's B. Correct retest displayed recovery confirmation, then loaded after 1,200 ms. The miss-during-remediation branch similarly selects another remediation prompt with generic dialogue. No per-question B is released/captured along these branches. The successful natural sequence was exercised; the active-remediation miss branch was source-traced. Decorative pause can keep five-second CSS-fading text visible, but cannot prevent a new question from replacing it.

**Canonical boss boundaries:** room 9's correct answer advances directly to the room-10 reveal rather than the normal hallway. Its B is skipped. A natural nine-correct-answer run consequently yielded eight entries. Three checkpoint responses, including a miss, yielded no additional entries. Individual responses use A/C and a 1,000 ms beat, then a manual checkpoint summary. The canonical post-summary hallway lasts 1,800 ms and contains checkpoint C, not question B. Managerial and Labyrinth use their own boss handling and narrative summaries; neither provides an individual-question explanation history for boss responses. Do not infer canonical three-response checkpoint rules for their non-Exam encounters.

**Exam release stages:**

1. Canonical/Economic/Macro: selecting an ordinary answer stores a draft and says it was saved. The choice can be revised. Entering the checkpoint commits the section and scores its drafts internally; it does not show an item-by-item answer/explanation review. Checkpoint responses use neutral “Response recorded.” text. After the third response, an outcome such as “MASTERY NOT YET SECURED” releases aggregate checkpoint performance. Final results and Mastery Report provide aggregate diagnostic information, not the questions' B. Thus “delayed feedback” does not mean a full explanation archive appears at the end.
2. Managerial parity: ordinary draft/commit behavior is similar. Each of three checkpoint responses is recorded without correctness text. Its manual summary says “CHECKPOINT COMPLETE / Your responses have been recorded.” It does not expose the canonical qualitative checkpoint judgment. Results provide aggregate performance. First-section draft/commit/checkpoint execution was reproduced for both Market Gate and Cost Directive.
3. Labyrinth: there is no equivalent section-draft branch in the effective `answer()` path. A correct Exam response immediately showed the complement-goods explanation, announced “Correct,” and advanced after 3.2 s; an incorrect response immediately opened Wrong Turn. Its mode description also describes adaptive practice without bosses. Review's `gameMode !== 'exam'` guard does not change this original delivery. The same unconditional hallway call exists in pre-cleanup commit `5e1d5644`. This is a confirmed cross-engine mismatch with the requested delayed-feedback policy, not evidence that Review introduced an answer leak.

**Screen-reader reading time:** manual feedback dialogs offer a substantially better opportunity to read before proceeding in modes without a global deadline. The current focus moves to their title; the body remains available for reading. This does not prove it is automatically spoken. Correct hallways put B in a polite status region, then replace that region with progress/guide text. Neither 1.8, 2.8, nor 3.2 seconds can reasonably guarantee completion of an arbitrary explanation. Actual announcement interruption, queuing, and virtual-cursor behavior require screen-reader testing.

**Would manual progression change gameplay?** Yes, even in an “untimed” mode: it changes the loading boundary, total elapsed time, and potentially recorded behavior. Standard, Unlimited, Quiz, and Trial by Graph are good candidates for an owner-approved pause at the already-scored explanation. Legendary needs a separate decision about its challenge/completion expectations. Timed Trial and Score Attack require explicit clock/scoring decisions. Fading Fortune has an already-frozen answered-item interval, but extending it still changes total time; Risk & Reward changes pacing and bust/results sequencing. None should silently gain new progression rules in a visual patch.

### Why Review was added, and what it actually records

The original audit's [A06 finding](C:/Users/Jennings/Documents/GitHub/masteryquests-website/docs/accessibility-cleanup-audit.md:42) identified released text that disappears and is difficult to revisit. It combined live announcements, motion control, and a feedback disclosure. The later refinement removed the ordinary-gameplay archive and restricted menu review to question explanations. Its motivation remains valid, but A06's broad “fixed/tested” conclusion is not sufficient evidence for every current lifecycle and engine.

The current collector reads only the current question's `feedback`, converts its HTML to normalized text, then requires a match against an active hallway's second child or a visible non-menu dialog. Dialog matches accept the explanation alone or the exact prefixes “Incorrect.”/“Incorrect!”. It does not use correctness as a filter and does not enumerate answer keys or banks.

The entry key combines question ID, question text, and explanation. Tested entries matched their original questions; unrelated guide speech and checkpoint narration were excluded. Repeated identical entries collapse into one; this is not a chronological attempt log and does not retain the chosen response or outcome. Capture depends on `feedback` metadata, the live `currentQuestion`, DOM structure, exact normalized text, and observer timing. A differently formatted delivery path could be missed. No such missed ordinary plain-text hallway/modal capture was reproduced in the 106-case suite. Rich HTML in faculty-authored feedback remains a portability edge: modal display uses `innerText`, while matching strips metadata HTML. That edge was source-identified, not reproduced with an authored-bank test.

Most “missing” questions therefore fall into two different categories:

- **Never released:** Wrong Turn, recovery, boss responses, pre-boss skip, or Risk bust. Capturing their metadata anyway would violate the release boundary. Any decision to teach from those explanations belongs to the owner.
- **Released but later unavailable:** completion/reset/reload clears the in-memory map. This undermines history's accessibility purpose. It is not evidence that the explanation was absent from the bank.

The original content is duplicated intentionally when it enters review. It is useful duplication while the source presentation is transient. Mastery Report evidence labels and instructional-resource recommendations are not substitutes for the exact question explanation. No report-based per-item B review was found in the traced paths.

For **2.2.1**, a content time limit needs an applicable turn-off, adjustment, extension, or exception path. The adjustment alternative spans at least ten times the default; the extension alternative includes at least twenty seconds' warning and at least ten extensions. An equivalent accessible route to the same information can avoid imposing a reading deadline; a particular permanent history widget is not prescribed. Merely offering a differently scored untimed mode is not proof of equivalence. The real-time and essential exceptions require justification; calling an activity a game does not establish either. [W3C Timing Adjustable](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html).

The actual AT question is whether users can discover, navigate, and finish B, not merely whether a live-region mutation occurred. Test NVDA/Firefox or Edge and VoiceOver/Safari with long explanations, rapid updates, paused motion, completion, menu review, and restored games. Include ordinary browse reading rather than only Tab navigation. The current dialog title receives focus and its text follows in reading order; the canonical dialog has no `aria-describedby` pointing to its body. This is not automatically a failure, but automatic reading of the explanation must not be assumed.

APG recommends focus inside modal dialogs, contained Tab navigation, a closing route, and return to a logical opener. Current menu Escape returned to its opener in focused tests; expanded graphs returned to the graph trigger. Continue-only feedback dialogs deliberately have no Escape cancellation path. Their Continue is keyboard operable, so this is not an inescapable keyboard trap, but an Escape behavior change must not silently acknowledge/advance a question. [APG modal dialog guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

## E. Three design alternatives

“Complete coverage” below means complete access to **already-released B**, not permission to expose explanations for every answered question.

| Alternative | Instructional value and accessibility | Interface complexity and compatibility | Gameplay risk |
|---|---|---|---|
| **1. Keep Review; improve presentation and coverage** | Reliable recall of released B can compensate for transient original delivery. Requires intentional completion/results availability and explicit release events instead of fragile display matching. Does not solve unreleased incorrect/recovery explanations. | One menu entry can open a focused reading view. Needs lifecycle rules, question association, empty states, and compatibility across overrides/standalone exports. Moderate maintenance. | Lower than changing progression, but not zero: reviewing during the next question affects response time; Timed Trial keeps running; Fading Fortune already pauses through the menu. Persistence/resume or release-boundary changes require approval. |
| **2. Remove history; make original B accessible** | Strongest direct teaching experience if B remains available until the student chooses to proceed. Existing manual wrong-answer dialogs are close to this model. Avoids reconstructing a separate archive. | Fewer controls and no duplicate list. Must make the original feedback region readable, focusable where appropriate, and consistent across engines. A universal version does not fit all mode contracts. | Manual continuation changes progression and elapsed time. Applying it to Timed Trial/Score Attack without clock/scoring decisions can distort intended challenge. Removing history first would worsen access. |
| **3. Accessible original B plus lightweight optional review** | Direct reading for instructional modes; recall of released B where timed/competitive auto-progression remains. Can preserve an after-run route without inserting controls into gameplay. | Slightly more logic than option 2, but far less menu clutter than a permanently expanded list. Requires clear mode eligibility and release/completion contracts. | Best fit if split into presentation work and separately approved progression/lifecycle work. Must avoid a new assessment leak or an unapproved timer pause. |

**Preferred destination: option 3, with option 2 as the default experience for suitable untimed instruction.** If owner-approved direct delivery later eliminates the demonstrated need for recall in a particular mode, its separate review option can be removed. Do not preserve history solely because the previous pass introduced it.

## F. Recommended visual refinements — not implemented

### Decorative Motion

Use one native, full-width button in the existing menu grid, matching the game's existing utility-button border, typography, spacing, colors, hover, and focus treatment. Show **DECORATIVE MOTION: ON** or **DECORATIVE MOTION: PAUSED** according to the effective setting. Do not place copies in questions, feedback dialogs, boss encounters, or reports. Collection hubs should use their existing menu/settings placement.

Retain `mq:accessibility:decorative-motion`. With no explicit stored choice, derive state from `prefers-reduced-motion`; activating the button stores the opposite effective state as `playing`/`paused`. Preserve cross-tab storage events, OS changes while using the default, page restoration, and graceful in-memory operation when storage is unavailable. Existing explicit choices must not be reset. Same-origin sharing cannot be promised between unrelated downloaded `file:` documents.

For the requested changing wording, use an ordinary native command button whose accessible name follows its full visible text, with a short description explaining that activation toggles decorative motion and a concise state announcement after activation. Keep focus on the button. Do not combine a changing label with a misleading `aria-pressed` convention. If choosing the APG toggle-button pattern instead, keep the accessible label stable and expose its pressed state consistently; agree that alternative wording before implementation. Enter and Space must both work. [APG button guidance](https://www.w3.org/WAI/ARIA/apg/patterns/button/).

The current selector also permits returning to “Use device setting.” A strict two-state replacement removes that visible reset choice. This is a small settings-design tradeoff to acknowledge; do not add an undocumented gesture or erase stored preferences to hide it. Motion pause must remain separate from question timers, fading-option rules, scoring, and music.

### Graph Description

Keep native `details`/`summary`, existing metadata resolution, full description text, graph enlargement, and keyboard behavior. Style the collapsed row as a compact part of the graph frame: inherited theme text, a restrained theme-colored border, and a visible disclosure indicator. Use real text for the label, preserve the focus outline, and allow the label to wrap.

**Place it visually inside the graph container, immediately below the image in document order.** Expansion should push following content down, never cover the graph or answer controls. Use the same arrangement in the enlarged view, retaining vertical scrolling and the current large image. On mobile, description text should wrap at the container width with no clipping or forced horizontal reading. Do not shorten, rewrite, or supplement descriptions with answer reasoning.

Native disclosure behavior supplies the interaction and expanded/collapsed semantics; do not replace it with a clickable decorative element or duplicate state management unnecessarily. Enter/Space operation and understandable expansion state match the [APG disclosure guidance](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/). No functional graph defect was established that justifies changing its content.

### Review, only where retained

Use one compact menu-style **Review Explanations** entry, optionally with a released-item count. Open a dedicated reading view within the existing modal framework instead of expanding the entire list among utility controls. Use a heading, the original question, and its released explanation; consider one expanded item at a time. Preserve full text and an ordinary scrolling reading area, with a clear Back/Close action and focus restoration. Do not add atmosphere, outcome guesses, answer keys, or generic encouragement.

This layout is justified only alongside a defined access lifecycle. A better-looking list that still disappears on completion does not fix the underlying problem. An after-run view must remain distinct from Mastery Report calculations and must obey each mode's release policy. Do not make ordinary gameplay carry a new panel or button.

## G. Final recommendation and decision boundaries

The least intrusive path is to keep the current application unchanged until these decisions are made, then separate the work:

| Presentation/accessibility work that need not alter protected mechanics | Owner decision required before implementation |
|---|---|
| Theme the single motion control while preserving its storage/OS behavior; agree how the former device-default choice is handled | Permit manual continuation at the original correct-explanation delivery point, mode by mode |
| Integrate the existing graph disclosure visually without changing metadata/text/enlargement | Define clock, elapsed-time, scoring, and response-time treatment when feedback is read |
| Preserve Labyrinth's heading/focus semantics when its existing game surface is restored | Decide whether Labyrinth's Exam Drill must adopt the other engines' delayed-release contract |
| Improve menu review layout without broadening what is released | Define review availability at completion, expiry, reload/resume, and mode changes; do not alter save schemas incidentally |
| Add targeted regression checks for release filtering, focus, and identical protected state transitions | Decide whether any currently unreleased wrong, recovery, boss, pre-boss, or bust explanation should ever be shown |

“Need not alter protected mechanics” is a proposed scope, not authorization to implement in this audit. In particular, do not simply move/remove `resetFeedback` calls without separating the review lifecycle from `beginRunSession`'s existing cancellation safeguards.

Future acceptance should compare question IDs/order, adaptive/remediation state, room/checkpoint progression, attempts, correctness, scores/streaks, timer boundaries, save/resume data, and telemetry/report outputs against the approved baseline. Changes to reading time need an explicit expected-difference specification rather than a claim that nothing changed. Repeat standalone generation tests only after an authorized source change, then test actual AT speech/reading behavior.
